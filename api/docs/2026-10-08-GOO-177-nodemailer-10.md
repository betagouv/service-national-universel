# Lot : nodemailer ≥ 10.0.9 dans api, apiv2 et snupport-api (GOO-177)

Périmètre : `api/package.json`, `apiv2/package.json`, `snupport-api/package.json`, l'override racine `package.json` (`overrides.mailparser.nodemailer`), `package-lock.json`.

## 1. Corrigé

| Paquet | Avant | Après |
| --- | --- | --- |
| `api` | `nodemailer@^9.1.1` | `nodemailer@^10.0.9` (installé : 10.0.9) |
| `apiv2` | `nodemailer@^9.1.1` | `nodemailer@^10.0.9` (installé : 10.0.9) |
| `snupport-api` | `nodemailer@^9.1.1` | `nodemailer@^10.0.9` (installé : 10.0.9) |
| copie imbriquée via `mailparser` (override racine) | `nodemailer@^9.1.0` | `nodemailer@^10.0.9` |

Édition chirurgicale du lockfile existant (4 entrées `node_modules/nodemailer` + 3 lignes de range), sans régénération complète : `lockfileVersion` et toutes les entrées non concernées (paquets optionnels de plateforme compris) restent identiques à `main`.

Sur `main`, la copie imbriquée tirée par `mailparser` était déjà résolue à `nodemailer@10.0.10` (mailparser 3.9.28 l'épingle dans son propre `package.json`, indépendamment de l'override racine) : elle n'était donc déjà plus vulnérable, malgré l'override `^9.1.0` affiché. Le correctif met quand même à jour l'override par cohérence et parce que le ticket le demande explicitement.

`npm audit --omit=dev` ne remonte plus d'alerte `nodemailer` dans aucun des trois paquets.

## 2. Changement cassant de nodemailer 9 → 10

Un seul changement cassant déclaré par nodemailer entre 9.1.1 et 10.0.0 : Node.js ≥ 20 requis (`CHANGELOG.md`, tag `v10.0.0`). Le dépôt impose déjà Node 20 (`engines.node` racine), donc sans impact. La 10.0.0 migre aussi la distribution vers TypeScript (`dist/cjs`/`dist/esm` avec carte `exports`) : les imports profonds utilisés ici (`nodemailer/lib/mailer` dans apiv2) restent résolus via cette carte, vérifié. Aucun autre changement d'API cassant dans les versions 10.0.1 à 10.0.9 (uniquement des correctifs : `addressparser`, DKIM, fetch) : les trois appelants (`api/src/mailcatcher.ts`, `snupport-api/src/mailcatcher.ts`, `apiv2/src/notification/infra/email/brevo/EmailBrevoCatcher.provider.ts`) n'utilisent que `nodemailer.createTransport(...).sendMail(...)`, API inchangée.

## 3. Non-régression

* Transport SMTP réel (hors mock) : `api/src/__tests__/mailcatcherTransport.test.ts`, `snupport-api/src/__tests__/mailcatcherTransport.test.ts`, `apiv2/src/notification/infra/email/brevo/EmailBrevoCatcher.provider.spec.ts` — un faux serveur SMTP reçoit un email réellement envoyé par `nodemailer.createTransport`.
* Analyse d'adresses par `mailparser` (copie de nodemailer la plus exposée aux alertes élevées, relève IMAP du support) : `snupport-api/src/__tests__/mailparserAddressParsing.test.ts`, avec la vraie bibliothèque.
* Version installée : `api/src/__tests__/nodemailerVersion.test.ts`, `apiv2/src/notification/infra/email/nodemailerVersion.spec.ts`, `snupport-api/src/__tests__/nodemailerVersion.test.ts` (ce dernier vérifie aussi la copie imbriquée résolue par `mailparser`).
* Suites existantes email/imap de l'api, d'apiv2 et de snupport-api relancées en série, toutes vertes.

## 4. Hors périmètre

Aucun changement de comportement d'envoi d'email ; uniquement la version de la dépendance et son override.
